The specific numbers QueryLens's engine runs with, for anyone checking a fact rather than reading a
concept explanation.

## Buffer pool

- **8 frames** by default in the Playground; adjustable 2–8 in the
  [standalone sandbox](/tools/buffer-pool) and forced to specific values by some
  [challenges](/challenges) and [Compare](/compare) modes, to make an algorithm's actual behaviour
  visible rather than hidden by a pool big enough to cache everything.
- **4 rows per page.**
- **Two replacement policies in the main pipeline** — LRU and clock sweep, switchable per query.
  The standalone sandbox adds four more for comparison: FIFO, second-chance, optimal (unbuildable
  for real; the fewest-misses bound the others are measured against), and midpoint LRU (what
  InnoDB does). See [The buffer pool](/docs/concepts/buffer-pool).
- Clock sweep's per-frame usage counter caps at **5**.

## B+Tree index

- **Any number of indexes per table** — plain single-column ones (`indexedColumns`) and **composite**
  ones (`indexes: [{ columns: ['city', 'age'] }]`, declared in the Custom database's *Manage tables*
  as `city+age`). Each is its own B+Tree. When several candidates each match an equality conjunct,
  the planner picks the one that pins the most rows down — the product of its matched columns'
  distinct-value counts.
- **A composite index is entered through a leftmost prefix.** An index on `(a, b)` answers `a = 1`
  and `a = 1 AND b = 2`, but not `b = 2` alone: its entries are ordered by `a` first, so the `b`
  matches are scattered through the whole index. The optimizer says so when it declines one. A range
  enters it through the leading column (`a > 5`), or — after an equality on the columns before it —
  through the next one (`a = 1 AND b > 5` walks just the run of entries for `a = 1`). A query that
  reads only the index's own columns is **covered** — an index-only scan returns them straight from
  the entries.
- **NULL leading columns are never indexed** (an equality on NULL is never true, so there is
  nothing to find); a NULL in a *later* column is an ordinary entry, so `(1, NULL)` is still found
  by `a = 1`. A `JOIN` can probe a composite index through its leading column.
- **Indexes are built when the query runs** — one entry at a time, in row order, by default. The
  setting `indexBuild` can *bulk-load* them instead (sort the entries, pack the leaves to a fill
  factor between 50% and 100%, build the levels above with no splits): a smaller, often shallower tree
  with identical answers. [Compare](/compare)'s *Index build* mode scores the three on 400 rows.
- **`UNIQUE`** is an index that refuses repeats: declare it in the Custom database's *Manage tables*
  (`Unique indexes: email, team+role`). `INSERT` and `UPDATE` look the new key up in the index first
  and, if it is taken, are rejected — the trace shows the lookup that found it, and **nothing changes**.
  NULLs never conflict. The check runs row by row in the order rows are visited, so a multi-row
  `UPDATE` that repeats a key part-way through (`SET id = id + 1`) is rejected, as PostgreSQL's
  immediate constraints reject it. There is no `CREATE UNIQUE INDEX`; a table whose rows already
  repeat a key cannot be given one (the editor refuses to apply it).
- **A table may be *clustered*** on one of its own `UNIQUE` indexes (`clusteredKey: ['id']`): its rows
  are stored in that key's order rather than insertion order, so a range on it reads pages in sequence.
  Every other index then carries the clustering key instead of the row's address — a clustered leaf can
  split and move rows between pages, the clustering key never does — so an equality lookup through one
  costs a second, real descent, through the clustered index itself; a covering query still costs only
  one. A range scan and an index-nested-loop join never choose a clustered table's secondary index, and
  fall back to a plan that does not need one. Not yet exposed in the Custom database editor — a seeded
  database can set it, the engine and its tests do not otherwise distinguish it from any other table.
- **Fan-out**: each node holds at most **4 keys** (5 children) before splitting; adjustable 3–6 in
  the [standalone sandbox](/tools/btree).
- Supported operations: **insert**, **delete** (borrow/merge/root-collapse), **point lookup**, and
  a **range scan** that descends once and walks the leaf sibling chain horizontally. All traced.
  See [The B+Tree index](/docs/concepts/btree).
- The planner uses the index for an equality (`WHERE id = 5`, an `IndexScan`), a range (`WHERE id >
  30`, `<`, `<=`, `>=` or `BETWEEN`, an `IndexRangeScan`), or — when the SELECT list needs nothing
  but the indexed column itself — an index-only lookup that never touches the heap at all. An
  equality always wins over a range when both are available, by rule order, not a cost comparison.
  A predicate on an unindexed column always runs as a sequential scan.
- **An indexed column may repeat.** An entry is the value plus the row's own address, so two rows
  with the same value are two entries, side by side in the leaves; an equality returns every match
  (walking the leaf chain for as long as the value holds) and costs one heap page per row. There is
  no `UNIQUE` — nothing stops a duplicate — and **NULLs are never indexed**, so `x IS NULL` scans.
  `DELETE`/`UPDATE` re-run the real `deleteKey`/`insert` algorithms against the one entry that
  belongs to each row; `UPDATE` re-indexes a row only when its own indexed column actually changed.

## JOIN

- **One `JOIN` per query**, an implicit inner join: `JOIN table ON a.col = b.col`, always an
  equality between one qualified column from each side.
- **Four algorithms** — nested-loop (the default), hash, sort-merge, and **index nested-loop** —
  chosen by whichever [Compare](/compare) forces; the engine never picks between them on its own.
  The index join probes the *inner* (`JOIN`ed) table's own B+Tree once per outer row, so it needs an
  index on that table's join column; without one it quietly runs as a plain nested-loop, and the plan
  says so. The other three never consult an index, and no `JOIN` side ever becomes an `IndexScan` —
  a `WHERE` conjunct on the outer table is pushed into its scan, but that scan stays sequential.
- Cannot combine with `GROUP BY`, `ORDER BY`, or an aggregate in the SELECT list.

## GROUP BY and aggregates

- `COUNT(*)`, and `COUNT`/`SUM`/`AVG`/`MIN`/`MAX` over a column.
- **Two strategies** — a hash aggregate (default) and a sort aggregate, which sorts the input on
  the `GROUP BY` columns first, spilling through the buffer pool exactly as `ORDER BY` does. Same
  groups out either way; [Compare](/compare)'s aggregate mode scores the difference in I/O.

## Writes

`DELETE`, `INSERT` and `UPDATE` all run for real and persist their effect — a write's changed rows
become the table's new contents for every query that follows. Each finds its target rows the same
way a `SELECT`'s `WHERE` would (an index lookup or a range walk of the index when it can, a scan
otherwise), takes an exclusive lock on every page it will change, and drops and re-adds exactly the
index entries of the rows it touches.

## Statistics

- **`ANALYZE table`** is a real statement: a real scan of the real table, producing — per column —
  a distinct count, a null fraction, the most-common values with their real frequencies, an
  equi-depth histogram over what is left, and how much the column's own order tracks the table's
  physical row order (correlation, `-1` to `1`; a [clustered table](/docs/concepts/btree) achieves
  exactly `1` on its clustering key). Shaped after PostgreSQL's own `pg_stats`.
- **The result *is* the statistics** — one row per column — shown in the same Result panel any
  other query's answer would be. There is no separate stats panel to open; opening the result is
  opening the statistics.
- **A snapshot, not a live fact.** Once run, a table's statistics sit on it exactly as they were the
  moment `ANALYZE` ran — even after later writes change the table underneath them — until `ANALYZE`
  runs again. A table that has never been `ANALYZE`d keeps the older, always-accurate-because-always-
  live behaviour every other v2.0 estimate already had: the planner scans the real rows itself.
  Nothing is `ANALYZE`d by default.
- **The cost model reads them when they exist.** An equality on a most-common value gets its real
  frequency instead of assuming every distinct value is equally likely; any other value gets the
  average of what the most-common list does not already cover, which is closer to `1/ndistinct` the
  less skewed the column is and further from it the more skewed; a range reads the histogram's real
  bucket boundaries instead of interpolating linearly between the column's min and max.
- **A statement, not a button.** Its answer travels through the trace, the URL, a saved moment and
  an assignment link the same way any other statement's does — there is nothing about `ANALYZE`
  itself that the rest of the app treats specially.
- **Single-column only — nothing records how two columns co-occur**, which is the independence
  assumption every `AND` in `WHERE` makes (`fraction × fraction`) and exactly where it can badly
  fail. The `employees` preset dataset is built to show it: `department` and `office` are perfectly
  correlated, so `WHERE department = 'x' AND office = 'y'` is no narrower than `department = 'x'`
  alone, but the optimizer estimates it as if the two were independent. `EXPLAIN ANALYZE` reports
  the gap as **q-error** (`max(est/actual, actual/est)`, the metric Leis et al.'s *How Good Are
  Query Optimizers, Really?* uses) beside any operator whose estimate is off by 2× or more — the
  `employees` headline query measures **11×**. Nothing here *corrects* for the correlation; naming
  it honestly is the whole feature.

## Locks

- **Page-level**, coarse-grained: one shared read lock per page, taken and released as a scan or
  descent visits it, upgraded to exclusive for the page a write actually changes.
- **Visual only** — QueryLens runs exactly one query at a time, so no lock ever actually waits on
  another. The panel draws what a real engine's lock manager would be doing, not an enforced
  constraint. The [locks sandbox](/tools/locks) simulates two transactions separately, with real
  blocking, deadlock detection and victim selection, outside the main pipeline.

## What's out of scope entirely

No subqueries, no more than one `JOIN` per query (so no join-order
choice), no outer joins, no transactions, no real
concurrency (the Locks panel is visual only), and no cost-based query optimization — every
rewrite rule fires on a structural match, never a cost comparison, and the cost *estimates* shown
alongside a plan exist to justify a rewrite's narration, not to decide whether it happens. `UNION` and `COUNT(DISTINCT …)` are also not accepted. These are deliberate exclusions for this
release, not bugs — see the parser's own error messages in [Supported SQL](/docs/reference/sql)
for exactly which keywords are recognised and rejected.
