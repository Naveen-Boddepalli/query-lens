---
title: Supported SQL
description: The exact SQL subset QueryLens's parser accepts, and what it says when you write something outside it.
---

QueryLens implements four statements — `SELECT`, `DELETE`, `INSERT` and `UPDATE` — over one table
at a time (two, for a `JOIN`). This page is the complete subset: if it isn't listed here, the
parser does not accept it yet, and it will tell you so by name rather than failing with a generic
syntax error.

## SELECT

```sql
SELECT * FROM users;
SELECT id, name FROM users WHERE age > 30 AND name = 'Ada';
SELECT * FROM users WHERE id BETWEEN 10 AND 20;
SELECT authors.name, posts.title FROM authors JOIN posts ON authors.id = posts.authorId;
SELECT status, COUNT(*), AVG(attempts) FROM logins GROUP BY status;
SELECT * FROM users ORDER BY age DESC LIMIT 5;
```

- **Column list**: `*`, a comma-separated list of columns, or aggregate calls (below). Not both at
  once — a plain column and an aggregate can only sit together when every plain column is also
  named in `GROUP BY`.
- **`FROM`**: exactly one table, plus an optional single `JOIN`.
- **`JOIN`**: a bare, implicit inner join — `JOIN table ON a.col = b.col`, always an equality
  between one qualified column on each side. No `LEFT`/`RIGHT`/`FULL`/`CROSS`/`USING`, and no more
  than one `JOIN` per query. Every column reference is qualified (`authors.id`, not `id`) once a
  query has a `JOIN` — there is no ambiguity resolution. A `JOIN` cannot combine with `GROUP BY`,
  `ORDER BY`, or an aggregate in the SELECT list.
- **`WHERE`**: any number of comparisons joined with `AND` (no `OR`, no `NOT`).
  - Operators: `=`, `<`, `>`, `<=`, `>=`.
  - `BETWEEN lo AND hi` — sugar for `col >= lo AND col <= hi`.
  - Literals: numbers, single-quoted strings, `TRUE`/`FALSE`, `NULL`.
- **`GROUP BY`**: one or more columns. Aggregates: `COUNT(*)`, `COUNT`/`SUM`/`AVG`/`MIN`/`MAX` over
  a column. Every plain column in the SELECT list must be grouped or wrapped in an aggregate.
  Mutually exclusive with `ORDER BY`.
- **`ORDER BY`**: exactly one column, `ASC` (default) or `DESC`.
- **`LIMIT`**: a non-negative integer, always the outermost clause.
- Keywords are case-insensitive, `--` starts a line comment, `/* */` a block comment, and a
  trailing `;` is optional.

## DELETE, INSERT, UPDATE

```sql
DELETE FROM users WHERE id = 5;
INSERT INTO users (id, name, email, age) VALUES (49, 'Ada', 'ada@example.com', 30);
INSERT INTO users VALUES (50, 'Alan', 'alan@example.com', 41);
UPDATE users SET name = 'Renamed', age = 31 WHERE id = 5;
```

- **`DELETE`**/**`UPDATE`** take the same `WHERE` grammar as `SELECT`, found the same way — an
  equality on an indexed column becomes an `IndexScan`, everything else a full scan.
- **`INSERT`** takes an explicit column list (any order) or none at all, meaning every column in
  table order; either way there is exactly one row per statement and every value is a literal — no
  expressions, no `SELECT` as a source.
- **`UPDATE`**'s `SET` values are literals only, same as `INSERT`'s `VALUES` — no reading one
  column to set another.
- All three persist for real: a write's changed rows become the table's new contents for every
  query that follows, in the Playground and in a challenge.

## What the parser recognises but rejects — on purpose

These keywords tokenise cleanly, so the parser can name exactly what you tried instead of failing
with a generic syntax error:

| You write | The parser says |
|---|---|
| `INNER JOIN` | *v0 supports a bare JOIN only — write JOIN without INNER.* |
| `LEFT`/`RIGHT`/`FULL` JOIN | *Outer joins are not in the v0 subset — only an inner JOIN.* |
| `CROSS JOIN` | *CROSS JOIN is not in the v0 subset — JOIN ... ON needs an equality.* |
| `JOIN ... USING (...)` | *USING is not in the v0 subset — write the equality out.* |
| A second `JOIN` | *Only one JOIN per query.* |
| `HAVING` | *HAVING is not in the v0 subset — filter before GROUP BY with WHERE instead.* |
| `OFFSET` | *OFFSET is not in the v0 subset — LIMIT on its own is.* |
| `DISTINCT` | *DISTINCT is not in the v0 subset.* |
| `UNION` | *UNION is not in the v0 subset.* |
| `OR` | *v0 supports AND only. Combine predicates with AND.* |
| `NOT` | *v0 supports =, &lt;, &gt;, &lt;=, &gt;= and BETWEEN, combined with AND.* |
| `<>`, `!=` | *Not supported yet — v0 supports =, &lt;, &gt;, &lt;=, &gt;= and BETWEEN.* |
| `CREATE` / `DROP` | *QueryLens only runs SELECT, DELETE, INSERT and UPDATE. Edit the seed data to change the table.* |

## The seed tables

Every query runs against one table at a time (two for a `JOIN`). The default is `users`, with
columns `id`, `name`, `email`, `age`; the **Data** chips above the editor also load `orders` (120
rows — a deeper index and a heavier scan) and `logins` (a lopsided `status` column, for
selectivity). Rows are editable from the app (**Edit data**), and both the choice of dataset and
any edits travel with a shareable link — see [URL parameters](/docs/reference/url-parameters).

The **Custom** data chip lets you build your own multi-table database in the browser — add a
table, declare one or more indexed columns, edit its rows, and `JOIN` across tables you built
yourself. It's kept in this browser only (`localStorage`), outside the shareable-link scheme.
