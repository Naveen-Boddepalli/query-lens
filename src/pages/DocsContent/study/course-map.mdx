## How to read this

Each topic gets one of three marks, and the words matter more than the symbol:

- **Covered** — you can watch the mechanism run, step by step, on a real (small) implementation of it.
- **Partly** — something real is here, but a large part of the topic is not.
- **Not covered** — nothing in QueryLens will help you with it. Use your course's material.

"Covered" never means *the way a production system does it*. Every number is true to this toy engine —
four rows to a page, eight buffer frames, four keys to an index node. What transfers is the *mechanism*;
[the FAQ](/docs/faq) and [the engine limits](/docs/reference/limits) say exactly where it simplifies.

## The map

| Topic | Coverage | Where to practise | What is missing |
|---|---|---|---|
| Relational model and algebra | Partly | The plan drawn as relational algebra — σ, π, ⋈, γ, τ, δ, λ — with **Show as → Relational algebra** on the [Playground](/playground)'s planner panel, and *Copy as LaTeX* for a homework answer | Set operators (∪, −, ×) and division; only the operators the engine executes |
| SQL | Partly | [Supported SQL](/docs/reference/sql): `WHERE` with `AND`/`OR`/`NOT`/`IN`/`LIKE`/`IS NULL`, arithmetic, `GROUP BY`/`HAVING`, `DISTINCT`, `ORDER BY`/`LIMIT`/`OFFSET`, one `JOIN`, `INSERT`/`UPDATE`/`DELETE`, and `EXPLAIN [ANALYZE]` — with results [checked against SQLite](/docs/reference/answers) | Outer joins, subqueries, more than one join, window functions, CTEs, DDL |
| Storage: heap files and pages | Covered | The [slotted-page inspector](/tools/page) lays a page out byte by byte; the Playground reads real heap pages | Variable-length overflow, free-space maps |
| Memory management: the buffer pool | Covered | [The buffer pool](/docs/concepts/buffer-pool), the [pool sandbox](/tools/buffer-pool) (LRU, clock, FIFO, second-chance, optimal, midpoint LRU), the [policy comparison](/compare), the *eviction storm* and *dirty eviction* [challenges](/challenges) | Pin/unpin contention between real concurrent queries |
| Log-structured storage | Covered | The [LSM tree sandbox](/tools/lsm): memtables, SSTable flushes, leveled *and* tiered compaction (pick either), Bloom filters with a real lookup path, and the write/space/read amplification it costs — plus a [B+Tree-vs-LSM comparison](/compare) with amplification from real counters on both sides | — |
| Storage models and compression | Partly | The [row-vs-column storage sandbox](/tools/columnar): NSM, DSM and PAX laid out three ways, with real compressed sizes for dictionary, RLE, delta and bit-packing, and the late-materialization trade-off that makes a column store pay off | The query engine itself still only ever stores and scans rows — the sandbox models columnar storage standalone, not wired into `EXPLAIN`/the Playground |
| Hash tables | Covered | The [Grace hash join sandbox](/tools/hash-join) (partitioning, spill, bucket collisions), the engine's hash join and hash aggregate, and the [extendible/linear hash index sandbox](/tools/hash-index) (directory doubling, local/global depth, round-robin splitting, and why neither scheme can answer a range query) | — |
| Tree indexes | Covered | [The B+Tree](/docs/concepts/btree): splits and merges in the [sandbox](/tools/btree), point lookups and range scans, **repeated keys**, **composite indexes and the leftmost-prefix rule**, **covering scans**, **`UNIQUE`**, bulk load vs one-at-a-time ([Compare → Index build](/compare)) | Clustered (index-organized) tables; secondary indexes that point at a key rather than a row address |
| Filters, tries, vector indexes | Partly | [Bloom filters](/tools/lsm) sized by bits-per-key, with a real lookup path and a measured false-positive rate | Tries, similarity search, vector indexes |
| Index concurrency | Covered | Latch crabbing, lock the child before releasing the parent: narrated in the [Locks panel](/playground), and contested on a scripted workload in the [latch-crabbing sandbox](/tools/latch-crabbing), naive latching against lock coupling side by side | Optimistic lock coupling; concurrent queries in the Playground still never contest a latch |
| Sorting and aggregation | Covered | The [external merge sort sandbox](/tools/sort), the engine's real spill through the buffer pool, hash aggregate vs sort aggregate and `DISTINCT` in [Compare](/compare), the *sort spill* challenge | Parallel and replacement-selection sorts |
| Joins | Covered | Nested-loop, hash, sort-merge and **index nested-loop**, forced onto one query in [Compare](/compare) — including the case where the index join *loses*; the *hash beats loop* challenge | Multi-way joins and join order; outer joins |
| Query execution models | Covered | The Volcano model, one row per pull down the operator tree, and a [tuple-at-a-time vs. batched comparison](/compare) that counts the `next()` calls each operator makes in one real run, against the batched count the same rows would need | Materialization (what a pipeline breaker holds in memory) |
| Parallel execution | Not covered | — | Multi-core operators, exchange |
| Query planning and optimization | Covered | The rule-based optimizer, one rewrite at a time in the [planner sandbox](/tools/planner); predicate pushdown, index selection, index-only scans; **`EXPLAIN ANALYZE`** with estimated rows beside the executor's actual rows | — |
| Cost models and join ordering | Covered | Row and page estimates on every plan node, `EXPLAIN ANALYZE` beside the executor's actual count, cost-based choice between an index and a scan, between join algorithms, and between join orders — each with a **Why not?** panel naming the runner-up — and [Selinger's DP search over the whole subset lattice](/tools/join-order) | Histograms beyond a few most-common values; only left-deep plans are enumerated, never bushy ones |
| Concurrency-control theory, timestamp ordering, MVCC | Not covered | — | Schedules, serializability, versions, snapshots |
| Two-phase locking | Partly | The [lock simulator](/tools/locks): shared/exclusive locks, waiters, deadlock detection and victim choice | Locks do not yet belong to the query engine's transactions |
| Logging and recovery | Not covered | — | WAL, checkpoints, ARIES |
| Distributed databases | Not covered | — | Replication, partitioning, consensus |

## Where it is strongest

If your course is at the *storage, indexing and query-processing* end, most of it is here and you can
run it: pages and the buffer pool, B+Trees in more shapes than a lecture has time for, the four join
algorithms, sorting and aggregation, and an optimizer you can step through. The
[interview roadmap](/docs/study/interview-roadmap) turns the same material into a six-week path.

## The biggest holes

Everything from **transactions onward** — concurrency-control theory, MVCC, logging, recovery,
distributed systems — is either absent or (for two-phase locking) a standalone tool outside the
engine. That is roughly a quarter of a typical course. Nothing on this page should be read as
covering it. Tries and similarity search are also absent.

If a topic above says *Not covered* and you need it, that is the right signal to reach for your
course notes or the textbook — not a gap in your understanding.
