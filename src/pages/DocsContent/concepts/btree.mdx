Without an index, finding one row means reading every page of the table — a **sequential scan**.
A **B+Tree index** turns that into a short walk down a tree: at each level, compare the key you want
against a handful of separator values and follow exactly one child pointer, until you land on a
**leaf** that either holds the row or proves it doesn't exist. For a table with thousands of rows,
that is the difference between reading thousands of pages and reading three or four.

QueryLens builds a real B+Tree over the seed table — internal nodes routing the search, leaf nodes
holding the actual keys, leaves linked in a sibling chain for range scans — and traces every step of
a lookup through it.

Step backward from there one event at a time and watch the highlighted path grow one hop at a time,
root to leaf — each step is one comparison, one child pointer followed.

## Reading the panel

- **Pink nodes are internal** — they hold separator keys and route the search, but never hold a row
  themselves.
- **Green nodes are leaves** — they hold the actual keys (and, in a real engine, either the row or a
  pointer to it).
- **The dashed line between leaves** is the sibling chain every B+Tree leaf level keeps, so a
  *range* scan (`WHERE age > 30`, say) can walk sideways across leaves once it finds the first one,
  instead of climbing back up to the root for each next value.
- The view frames only the current hop plus its parent, rather than the whole tree — a realistic
  B+Tree over even a small table is far wider than a screen, and the root-to-leaf path is the part
  that carries the lesson.

## Splits, and why fan-out matters

Each node in QueryLens's tree holds at most 4 keys before it **splits**: a full node divides into
two, and the middle key is pushed up into the parent as a new separator. That number — the tree's
**fan-out** — is the whole reason a B+Tree is fast. A higher fan-out means fewer levels for the same
number of rows, which means fewer pointer follows, which means fewer page reads, which is the entire
point of building the index in the first place. Real database indexes tune fan-out to match a disk
page's size — often hundreds of keys per node — precisely to keep the tree as shallow as possible.

Deletion is the split rule run backwards. When a node drops below half full it first tries to
**borrow** a key from a sibling; if neither sibling can spare one, the two nodes **merge** and the
separator between them comes out of the parent — which can cascade upward until the root itself
collapses into its only child. The [B+Tree sandbox](/tools/btree) lets you insert, delete and find
against a live tree and watch exactly that, with a fan-out slider and the structural invariants
re-checked after every edit.

## When a value repeats

An index on `authorId` has a problem the one on `id` never did: **the same value belongs to several
rows**. A tree that stores each key once has nowhere to put the second `authorId = 1`. The fix databases
use (InnoDB and PostgreSQL both) is to make the *row's own address* the tie-breaker: an index entry is
`(value, page, slot)`, so two rows with `authorId = 1` are two different entries — `1 @ page 0, slot 2`
and `1 @ page 1, slot 0` — sitting next to each other in the leaves. The tree itself never holds a
duplicate, so splits, borrows and merges work exactly as before.

What changes is the *lookup*. There is no single "the" entry for `authorId = 1`, so the search descends
toward the **first** one — and when a value equals a separator on the way down, it goes *left* of it,
because a run of equal values can straddle a separator and the first of them may be on the far side. Then it
reads along the leaf for as long as the value holds, and hops to the sibling leaf only if the leaf's
**high key** (its parent's separator — real engines store it on the page) says the value continues. A
unique value is the same walk that happens to stop after one entry.

Every entry the lookup finds is a heap page to fetch, so a value that repeats a hundred times costs
about a hundred page reads however shallow the tree is. That is exactly why an index on a column with
few distinct values is often *worse* than a scan. Try
[`SELECT * FROM posts WHERE authorId = 1`](/tools/planner?q=SELECT%20*%20FROM%20posts%20WHERE%20authorId%20%3D%201)
in the Planner sandbox — `posts` is indexed on `authorId`, which repeats (four authors, ten posts) — and read
the row estimate the cost model gives the `IndexScan`.

## Composite indexes and the leftmost-prefix rule

An index can be over more than one column. An index on `(city, age)` holds entries ordered by `city`
first and, *within* each city, by `age` — like a phone book ordered by surname, then first name. That
order is what decides which questions it can answer:

- `city = 'oslo'` — yes. All the Oslo entries sit together, so the search descends to the first one and
  reads along the run. This is a **leftmost prefix** of the key.
- `city = 'oslo' AND age = 30` — yes, and narrower: the run for that pair.
- `age = 30` alone — **no.** The people aged 30 are scattered through every city's run; there is no
  contiguous stretch of the index to read. The index is not entered, and the plan says so.

Because every column is in the entry, an index also *covers* a query that needs nothing else:
`SELECT city, age FROM people WHERE city = 'oslo'` never touches the heap — the entries answer it, which
is the same saving as an index-only scan, for more than one column.

Try it in the Playground's **Custom** data: add a table, and declare `city+age` under *Composite
indexes*.

## Where this simplifies

QueryLens's tree has a small, fixed fan-out (enough to demonstrate a split without needing thousands
of rows). It supports point lookups, range scans, inserts, deletes and key updates through the
pipeline, and repeated values as above. A
production index also handles — critically — concurrent modification, which is where the
[locking the app's Locks panel visualises](/) actually earns its keep in a real engine: two
descents that briefly hold two levels of the tree at once ("latch crabbing") are how a B+Tree stays
correct while more than one query touches it at the same time. QueryLens runs exactly one query, so
that layer is drawn but never actually contested.
